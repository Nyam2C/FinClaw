# FinClaw plan/kickoff 집(house) 양식

plan-author 가 따를 양식. **원본은 가장 최근 `plans/phase*/{kickoff,plan}.md`** — 항상 최신 phase 를 직접 읽어 어조·표·구조를 맞춘다. 아래는 phase40 에서 증류한 골격이다(최신과 다르면 최신 우선).

## 파일 2단 구조

- `kickoff.md` — 작업 시작 시점의 동기·범위·**"plan 이 반드시 결정할 것"**(열린 질문 목록). plan 보다 짧다.
- `plan.md` — kickoff 질문의 해소 + 확정 아키텍처 + 마일스톤. 승인 게이트 대상.

## plan.md 헤더 (관행)

```
# Phase {NN} 계획 — {한 줄 제목}

> 작성 {YYYY-MM-DD} · base = main HEAD `{sha}` ({직전 phase}) · 선행: plans/phase{NN}/kickoff.md
> 상태: **초안 — 사용자 승인 대기.** 승인 후 todo.md 분해 → 코드. (코드 전 plan 승인 게이트.)
```

## plan.md 필수 섹션 (phase40 기준)

```
## 0. 목표와 경계
   - 한 줄 목표("= 먼저 작동" 처럼 검증 가능한 성공 기준)
   - 경계(명시적 비대상): 이번 phase 가 안 하는 것 + 어느 후속 phase 로 미루는지

## 1. ★ 확정된 아키텍처 — {A/B/C 라벨}
   - ASCII 다이어그램으로 데이터 흐름
   - "왜 이 선택인가 (조사 근거)" — 리서치 보고서(_workspace/.../20-*.md) 인용, 기각된 대안의 기각 사유
   - "검증된 전제 (조사 완료)" vs "유일한 미확인 (Milestone A go/no-go)" 분리
   - 기존 레퍼런스(OpenClaw 등) 충실도가 있으면 표기

## 2. kickoff "plan 이 반드시 결정할 것" N개 — 해소
   - | # | 항목 | 결정 | 표

## 3. 마일스톤 (각 = typecheck+build+test+lint green, 1커밋)
   ### A. {go/no-go 스파이크 권장} — 게이트
   ### B. ...
   - 각 마일스톤: 무엇을·검증 방법(어떤 테스트)·커밋 단위

## 4. 스코프 IN / OUT
   - IN: 이번 phase 산출
   - OUT (phase{N+1}+): 미루는 것

## 5. 리스크
   - 각 리스크: 내용 + 완화책/폴백 + 되돌리기(안전판)
   - #1 은 보통 go/no-go 미확인 전제

## 6. 컨벤션
   - 테스트 baseline: unit {N} / storage {N} (최신 phase 수치 인용)
   - mock-only 유지 — 실 키/네트워크 테스트 금지, 라이브는 수동 검증 분리
   - 밀스톤당 1커밋, 외과적 변경(CLAUDE.md §3)
```

## 어조·스타일

- 한국어, 간결한 명사·종결("~한다", "~기각"). 불릿·표 중심.
- 결정에는 항상 **근거**. "왜 X 인가" 를 조사 인용으로 받친다.
- 기각된 대안을 적되 기각 사유를 명시(나중 재논의 방지).
- `★` 로 가장 중요한 결정(아키텍처) 강조하는 관행.
- 미확인은 "유일한 미확인 (go/no-go)" 으로 솔직히 분리 — 은폐하지 않는다.

## 하류 계약 (finclaw-phase-execute 가 todo 로 분해 가능하려면)

- 마일스톤이 **검증 가능한 단위**여야 한다(green + 1커밋). 모호한 "잘 만든다" 금지.
- 각 마일스톤이 건드릴 패키지/모듈을 짚어둔다(todo-architect 가 파일 단위로 쪼갬).
- 첫 마일스톤을 go/no-go 스파이크로 두면 가장 큰 미확인을 일찍 실증 → 폴백 비용 최소.
- 스코프 OUT 이 명확해야 todo 가 범위를 넘지 않는다.
